# 新コース実装計画：タガログ語 日常フレーズ集（`tl-phrases-daily`）

Kohei 承認済み（2026-08-05）。**この計画に沿って実装する。**
計画の策定は Opus（planner）、実装は Sonnet で進める前提で、判断が要る箇所は先に潰してある。

## 0. 決定事項（確定・再検討不要）

| 論点 | 決定 |
|---|---|
| 規模 | **450フレーズ** |
| 訳の言語 | 日本語 |
| コース区分 | tl-0-2k（単語コース）とは別の新規コース |
| 話者設定 | **Kohei（日本人HR）がフィリピン人スタッフ・候補者に話す前提**（Kohei判断・2026-08-05）。逆にすると職場・面接カテゴリの主語・敬語方向が丸ごと作り直しになるため最初に固定 |
| Taglish（英語混じり） | **職場・会議系は許容する**（Kohei判断）。フィリピンの職場は英語とタガログ語のコードスイッチが実態のため、純タガログ語にすると「誰も言わない文」になる |
| IPA発音記号 | **v1では付けない**（推奨案採用）。アクセント表記（`reading`）で足りる。文全体のIPAはタイルに収まらず、生成・検証コストも倍になる。`ipa` は cardId のキーに含まれないので後から無傷で追加できる |

| カテゴリ配分 | 職場・実務を厚めに（下記§2） |
| データ生成方式 | **AI生成が主軸、Tatoebaは検証補助**（実測に基づく結論。§1） |
| cardIdキー | 内容（headword/reading）ではなく**不変のslotId**をキーにする（`idKey` を`card_id.py`に追加。§3） |

## 1. 実測データ（この計画の前提。調査済み）

### Tatoebaはフレーズ集の主軸にできない

`pipeline/raw/tgl_sentences.tsv.bz2` / `tgl-eng_links.tsv.bz2` を実測：

| 指標 | 実測値 |
|---|---|
| タガログ語文の総数 | 79,040 |
| 英語対訳リンクを持つ文 | 37,624 |
| po/ho（丁寧語）を含む文の割合 | 16.9% |

量はあるが、定番の日常フレーズ22件で検索した結果、**完全一致は22件中1件以上ヒットしたのが4件のみ**（合計6ヒット）。役所・書類系はコーパス全体で11件のみで内容も無関係。**Tatobaタガログ語は「英語文の翻訳コーパス」であり「フィリピン語のフレーズブック」ではない**。よってAI生成を主軸にし、Tatoebaは自然さの検証（attestation）補助として使う。

### tl-0-2kの既存例文（生成の参考素材）

出荷済み例文2,332件（欠損0件）。文字数中央値24／p90=40。語数中央値4／p90=7。例文トークンの78.5%が2,000見出し語で覆われる（下限値）。検証済みのタガログ語×日本語ミニ文コーパスとして、語彙ゲート基準・一部スロットの素材に使う。

### 見出し語の長さ（UI設計の根拠）

tl-0-2kの例文2,332件を「もし見出し語だったら」として測定：

| 表示ユニット数 | 割合 |
|---|---|
| ≤20 | 35.5% |
| 21–30 | 37.5% |
| 31–40 | 17.8% |
| 41–50 | 6.0% |
| >50 | 3.2% |

現行の `headwordFit.ts` は9文字→`hw-lg`(27px)、13文字→`hw-xl`(21px)で打ち止め。**64.5%が最下段の21pxに張り付く**。フレーズコースでは見出し語を実測フィット（`useFitText`）に切り替える必要がある（既存の単語コースのパスは変更しない）。

## 2. データ設計

### 2.1 VocabCardフィールドの割り当て

| フィールド | 用途 | UIでの出方 |
|---|---|---|
| `headword` | タガログ語フレーズ全文（句読点込み） | タイル表面。**要フィット処理改修** |

| `ipa` | v1では未設定 | — |

| `pos` | 発話機能ラベルに転用 | 例:「質問（値段）」「依頼」「相槌」「断り」。Browse画面のチップのみ |

## 3. データ生成パイプライン設計

### 3.1 4層ハイブリッド構成

```
L0 スロット表（人＋AIで先に固定・git管理）
   450件 × { slotId, category, function, intent_ja（達成したい目的）, register, speaker }
   ※ 日本語の定型文を訳させるのではなく「目的」を定義する（文化的適切さの対策の本体）
        ↓
L1 生成（Workflow fan-out・Sonnet固定・25〜30スロット/バッチ×16バッチ）
   headword / reading / gloss / pos / root / examples[0..1]
        ↓
L2 機械検証（LLM不使用・スクリプト。ここで大半を落とす）
   ①slotId全件1回出現・headword重複なし
   ②register=politeの行にpo/hoがあるか
   ③語彙ゲート：headwordの各トークンがtl-0-2k見出し語に含まれる率（目標≥70%）
   ④Tatoeba照合：bigram/trigramが79,040文に出現するか（attestation。0の行だけ人手裁定へ）
   ⑤文字種・NULバイト検査・JSON schema・validate_records()
        ↓
L3 AI多段検証（Workflow・観点を分割した2人＋裁定者）
   検証A【言語】文法・アスペクト・綴り・アクセント位置・po/hoの一貫性
   検証B【場面】日本語訳がL0の「目的」と一致するか・敬語方向・話者・実際に言うか
   不一致→3人目（Opus）が裁定→修正はL0/L1のソースに戻して反映（出荷物を直接触らない）
```

検証A・Bを分けるのは、言語的正しさと場面的適切さの失敗モードが独立しているため。

### 3.2 Workflow運用の必須ガード（過去の実測教訓）

- `agent(prompt, { model: 'sonnet' })` を必ず明示（未指定はOpus継承）
- 1バッチ25〜30件厳守
- 検証段は陽性（要修正）のみ出力。全件エコー禁止
- ツールをRead/Writeに限定＋呼び出し回数上限を明記
- 大配列は`args`で渡さずスクリプトにJSリテラル埋め込み
- Windows生成の.jsは`newline="\n"`必須（CRLFはWorkflowに拒否される）

コスト見積り：生成16＋検証32＋裁定数体≈55体。1〜2セッション枠で完走見込み。

## 4. cardId・進捗管理・ビルドの冪等性

### 4.1 idKeyの導入（card_id.pyの後方互換拡張）

既存の `content_key(headword, reading)` は単語コースでは正しいが、フレーズは文言の推敲（表現の調整）が起きる前提なので、表層テキストをキーにするとcardIdが飛ぶ。`assign_ids()`に任意の`idKey`を追加し、フレーズコースはL0で確定した不変の`slotId`（例: `work-012`）をキーにする。

```python
key_head = r.get("idKey") or r.get("headword")
key_read = "" if r.get("idKey") else r.get("reading")
found = reg.lookup(key_head, key_read, gloss, rank)
```

既存9コース（idKeyを持たない）の挙動は完全に不変。**変更後は`pipeline/test_id_stability.py`を9コース全部で緑にすることを完了条件に含める**（card_id.pyは全ビルド共通の採番経路のため）。

### 4.2 「中間データと出荷物の非同期」の再発防止

前回tl-0-2kのIPA配線時に発覚した問題：`pipeline/raw/`が`.gitignore`対象（`.gitignore:35`）のため、中間データがバージョン管理外になり、出荷済みJSONとの非同期が起きた。新コースでは：

1. **キュレーション済みソースは`pipeline/data/tl-phrases-daily/`にgit管理で置く**（`pipeline/raw/`は「ダウンロードした第三者コーパス専用」に用途限定）
2. ビルドスクリプトは純関数にする（突合の推定・重複の間引き・定員切り捨てを禁止。入力が不正なら大きな声で落とす）
3. **`--check`モードを実装**：一時ディレクトリに再ビルド→出荷済みとバイト比較→差分があればexit 1
4. 決定性の担保：並び順はslotId固定、`json.dump(separators=(",",":"))`

## 5. UI設計

### 5.1 CourseTypeの新設

`coverage.ts`の`courseProgress()`に`case 'phrase':`を追加（`kana`と同じsize-depthを返す）。`CourseScreen.tsx`の`course.type !== 'kana'`を述語に置換。i18nに「phrases」の文言。実装量は30行程度。

### 5.2 見出し語のフィット処理

フレーズ型コースの見出し語だけ`useFitText`（実測フィット）に切り替える。単語コースの既存パス（`headwordFit.ts`の静的閾値）は一切触らない。

### 5.3 その他の必須UI修正

| 箇所 | 問題 | 対応 |
|---|---|---|
| `.tile-reading` | `white-space: nowrap; text-overflow: ellipsis`で長文が切れる | 折り返し可に変更 |
| `.tile`固定高158px | 裏面が5ブロック（見出し・読み・訳・返答例TL/JA）で窮屈 | `--tile-h`をCSS変数化し、フレーズコースのみ196px程度に |
| `FocusSheet` | スマホの主戦場 | 幅に余裕あり。実機確認は必須 |
| `AllWords.tsx`/`WordSearch.tsx`/`CoursePreviewScreen.tsx` | 長文での横スクロール | 320–1366px横断チェック |
| `CourseScreen.tsx`の`TICK_STEP` | `Record<CourseId, number>`で網羅性がコンパイラ強制 | 新コースを1行追加（忘れるとtscが落ちる＝安全） |

### 5.4 コード変更点（全6箇所）

1. `src/types.ts` — `CourseId`union に1行
2. `src/types.ts` + `src/data/coverage.ts` + i18n — `CourseType`に`'phrase'`
3. `src/data/courseRegistry.ts` — `AVAILABLE_COURSES`に1件（**末尾に追加**。配列順が初回既定コースを決める）
4. `src/features/CourseScreen.tsx` — `TICK_STEP`に1行
5. `src/data/categories.ts` — 新規カテゴリキー4件
6. `public/data/courses/tl-phrases-daily/` — meta.json / manifest.json / words-*.json / categories.json

⚠️ `withRealFallback`（`realRepository.ts`）は、登録済みでデータが無いと黙って別コースのモックデッキを表示する。**登録は出荷データが揃った最終フェーズで行う**。
